# RCA — "it did not post to facebook" (golumo.app)

Deployment: lumo-bundle-checkout · Active run: 470b2852-ec94-4c96-91ff-c41db191d02d (redeploy, success, Cloudflare frontend)
Prod DB: lumo-bundle-checkout-lumo_database

## Exact failing step + error
`POST /api/admin/city-blog/publish-facebook?count=10` → **400 Bad Request** ("Connect Facebook first").
Observed in prod logs (active run): `104.23.225.70 - "POST /api/admin/city-blog/publish-facebook?count=10 HTTP/1.1" 400 Bad Request`.
Consequence: no background job was created and nothing was posted → `city_blog_config {id:"fb_publish_job"}` is **absent** (count 0), `social_posts {platform:"facebook"}` is **empty** (count 0).

## Root cause
Facebook was never successfully connected — no Page access token was ever saved, so the publish endpoint rejects with 400.

Evidence:
- `social_channels` facebook doc = `{ enabled: false, page_id: "1194616753727437" }` — **no `access_token` field**, `enabled:false`.
- The OAuth **callback `/api/social/facebook/callback` was NEVER hit** — it does not appear in any logs over the last 24h. Only `/api/admin/social/facebook/authorize` (200, 3×), `PUT /api/admin/social/config/facebook` (200), and `/api/admin/social/facebook/status` (200) were called.
- In `fb_oauth.py`, only the callback's `_save_page()` sets `enabled:True` + `access_token` + `page_name`. Since the callback never ran, the token was never stored. The `page_id` present on the doc came from the manual `PUT /api/admin/social/config/facebook`, not the OAuth flow.
- `authorize` returns a JSON `{url: <Meta dialog>}` (hence the 200, not a 302). The browser must then go to Meta and Meta must redirect back to `META_REDIRECT_URI`. No callback hit our server → the Meta dialog was either not completed/approved, or Meta refused the redirect (redirect_uri not whitelisted / app in Dev mode / admin not a tester / required perms not granted).

## Everything else checks out (ruled out)
- **Env vars**: all present & non-empty — META_APP_ID, META_APP_SECRET, WEBHOOK_CRON_SECRET, ADMIN_EMAILS, EMERGENT_LLM_KEY. Verified exact values: META_GRAPH_VERSION = `v24.0` ✓, META_REDIRECT_URI = `https://golumo.app/api/social/facebook/callback` ✓, PUBLIC_BASE_URL = `https://golumo.app` ✓. So the redirect URI on our side is correct.
- **Deployed code**: `fb_oauth.py`, `city_blog.py`, `attribution.py` (and `social_publisher.py`) are all present in the active run's image (`ls` in eph sandbox). The latest deploy DID include them.
- **Image endpoint**: `GET /api/img/city/delhi-in.jpg` → 200 `image/jpeg` ✓ (photo-post source works).

## Secondary issue (will block publishing even AFTER Facebook is connected)
The `EMERGENT_LLM_KEY` budget is exhausted. `[city_blog]` cron is logging, repeatedly:
`litellm.RateLimitError: OpenAIException - Budget has been exceeded! Key=d8tvf5juu10s73ctkvp0 Current cost: 1029.69, Max budget: 1029.27` → recent runs "published 0/15 posts".
`publish-facebook` generates any missing `copy_version 2` posts via the LLM **before** posting, so once Facebook is connected this budget error will cause the job to fail on copy generation. (Earlier failures were JSON parse errors like "Expecting value: line 1 column 1"; now it's the hard budget cap.)

## Fixes
1. (User) Re-run Connect Facebook in /admin?tab=autopost and FULLY complete the Meta dialog — approve permissions and select a Page you can post to. After success, `social_channels` facebook should flip to `enabled:true` with an `access_token`.
2. (User / Meta app config — third party) In the Meta App (Facebook Login → Settings) confirm `https://golumo.app/api/social/facebook/callback` is listed under Valid OAuth Redirect URIs, the app is in Live mode, and the connecting admin is an app admin/tester with the pages_manage_posts / pages_show_list scopes. This is why Meta never redirected back to the callback.
3. (User) Top up / raise the Emergent LLM budget (EMERGENT_LLM_KEY) so copy generation inside publish-facebook and the city_blog cron stop failing with "Budget has been exceeded".

No code change required — source path is correct, files are deployed, and all relevant env values are correct.
