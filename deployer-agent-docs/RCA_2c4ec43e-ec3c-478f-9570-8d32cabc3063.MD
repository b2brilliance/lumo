# RCA — "Site only loads in incognito/private tabs" (lumo-bundle-checkout / golumo.app)

## Problem statement
Returning visitors report the live site loads in incognito/private windows but not in normal browser tabs. 6th recurrence. Suspected stale cached HTML/JS or service-worker state.

## TL;DR
The **server, CDN/edge and build are completely healthy** — correct cache headers, current build, both domains serving the identical build, every referenced JS/CSS chunk resolves 200. **A redeploy alone fixes nothing and the problem will keep recurring**, because the cause is in the app's own client-side cache-busting code.

The concrete, provable defect: the frontend build stamp and the backend `/api/meta` build stamp **never match**. The inline "boot cachebuster" in `index.html` compares the two and therefore *permanently* believes the build is stale — so on essentially every normal-browser session it unregisters service workers, wipes Cache Storage, and force-reloads the page. That self-inflicted churn is what returning (normal-tab) users experience as "the site doesn't come up / I have to use incognito." Incognito starts clean each time so the churn is less visible, and devices already pinned to a legacy fetch-intercepting service worker from an old build are never reachable by the self-heal.

---

No aggressive HTML caching, no bad redirects. Headers are not the problem.

### 2. Is the production build current? — YES
Live `index.html` references `/static/js/main.b1dcf11b.js` + `/static/css/main.4860f396.css`; **both return 200**. There is **no** stale HTML pointing at deleted chunks on the server.

### 3. CDN caching / redirects on the custom domain — CLEAN
`golumo.app`, `www.golumo.app` both verified, SSL active, serving 200. DNS linked. No redirect/caching anomaly at the edge.

### 4. Do the custom domain and the emergent domain serve the same build? — YES
`golumo.app` and `lumo-bundle-checkout.emergent.host` return the **same** asset hashes (`main.b1dcf11b.js`, `main.4860f396.css`) and matching ETags. Identical build.

### 5. Build-stamp consistency — **MISMATCH (the defect)**
| Source | buildTime |
|---|---|
| `<meta name="lumo-build">` in live HTML (frontend) | `2026-10-02T01:18:22.177Z` |
| static `/meta.json` (frontend, on R2) | `2026-10-02T01:18:22.177Z` |
| **backend `/api/meta`** | **`2026-10-02T01:13:14.496Z`** ← different |

The backend value is byte-identical to the **git-committed** `frontend/public/meta.json` (`2026-10-02T01:13:14.496Z`).

---

## Why the two stamps never agree (mechanism)

- `frontend/package.json` runs `prebuild: node scripts/write-meta.js`, which on every `yarn build` generates a **fresh** `buildTime` and writes it to `public/meta.json`, `build/meta.json`, and injects `<meta name="lumo-build">`.
- This is a **Cloudflare frontend**: `build-frontend-artifacts.sh` runs `yarn build` and uploads `build/` to R2. So the R2-served frontend carries the **fresh** stamp (`01:18:22`).
- The **backend image** is built separately (`Dockerfile.cloudbuild`) and does **not** run `yarn build`. `/api/meta` (server.py ~L5700) reads `/app/frontend/build/meta.json` then falls back to `/app/frontend/public/meta.json`. In the backend image `build/meta.json` doesn't exist, so it serves the **committed** `public/meta.json` = `01:13:14` — stale, and generated by a different process than the R2 frontend.

Result: frontend stamp and backend stamp are produced independently and will essentially **never** be equal.

## How that produces the symptom
The inline boot-cachebuster `<script>` in `index.html` does (de-minified):
```
t = <meta lumo-build>            // 01:18:22  (frontend)
fetch('/api/meta').buildTime     // 01:13:14  (backend)
if (buildTime && buildTime !== t)     // ALWAYS true
    -> unregister ALL service workers
    -> delete ALL Cache Storage
    -> location.replace(url + '?_cb=' + buildTime)
```
It is throttled to once per ~15s per session (sessionStorage `lumo_boot_cachebuster_last`), so it's one forced SW-unregister + cache-wipe + reload **per fresh session** — i.e. every time a returning user opens the site in a normal tab. The comparison can never reach "equal/stop", so the self-heal is stuck permanently ON. `CacheBuster.jsx` compounds the confusion by trusting `/api/meta` first (01:13) while the boot script trusts the meta tag (01:18).

This self-inflicted reload/SW churn on normal sessions — plus any device still pinned to a legacy fetch-intercepting service worker from an older build that the self-heal cannot reach — is the "only works in incognito" behavior, and the reason it recurs after every deploy.

## Note on service workers currently shipped
None of the **current** SWs (`service-worker.js` killswitch, `sw-nuke-v3.js`, `push-sw.js`) has a `fetch` handler, so the current build cannot itself create a stale-HTML-serving SW. The residual hard failures on specific devices come from **legacy** SWs from old builds; those devices need a one-time reset (the app already ships `/reset`). This is per-device and cannot be fixed server-side.

---

## Fixes

### A. Code (E1) — required; this is the real fix
Make the frontend and backend build stamps agree (or stop cross-comparing them):
- Preferred: drive `buildTime` from a single source identical in both builds — e.g. set it to the deploy TAG via an env var that both the frontend build and `/api/meta` read; **or** copy the frontend's generated `build/meta.json` into the backend image during the backend build so `/api/meta` serves the real shipped stamp.
- Alternatively, make the boot-cachebuster compare like-for-like (frontend `<meta lumo-build>` vs the static `/meta.json`, both from the same build) instead of meta-tag vs backend `/api/meta`.
- Strongly recommended cleanup (root of the 6× recurrence): collapse the overlapping machinery (`service-worker.js` + `sw-nuke-v3.js` + inline boot script + `CacheBuster.jsx` + `/reset`) into ONE strategy. With static assets on CDN, correct `no-store` HTML and `immutable` hashed chunks already in place, a general service worker isn't needed — keep only `push-sw.js` (registered strictly on push opt-in) and drop the perpetual nuke/boot-reload logic.
Then redeploy. **A redeploy without this code change will reproduce the same mismatch.**

### B. User — only for devices already stuck right now
On any device currently showing the stale/blank page in a normal browser, visit `https://golumo.app/reset` once (or clear site data for the origin). This is a one-time per-device action and cannot be done server-side.

## Verification done / not done
- Verified via live HTTP probes (headers, asset resolution, both domains, build-stamp values) and source inspection in an isolated sandbox.
- NOT reproduced: the browser-side legacy-SW interception itself (requires a real browser carrying old SW state; no tool for that). The server-side health and the stamp mismatch are directly proven above.
